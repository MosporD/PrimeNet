Add IKE Proposal (ADD IKEPROPOSAL)

Network Element: BTS3900, BTS3900 WCDMA, BTS3900 LTE, BTS3900 5G, BTS5900, BTS5900 WCDMA, BTS5900 LTE, BTS5900 5G

Function

Use this command to add an IKE proposal.

Note

This is a high-risk MML command. Pay attention to the following precautions before running this command:

  • System specifications: If the WMPT/UMPT/UMDU/LMPT/GTMUb/GTMUc is the main control board, a maximum of 99 IKE proposals can be configured.

  • Board specifications: A maximum of 99 IKE proposals can be configured on a UMPT/UMDU/LMPT/UTRPc/UCCU/UBBPe (excluding UBBPe15)/UBBPei/UBBPep/UBBPem/LCOP/UBBPex2/UBBPf1/UBBPf0/UBBPg1/UBBPg2/UBBPg3/UBBPg4/UBBPg5/UBBPg6/UBBPg7/UBBPg9.

  • The IKEPROPOSAL MO takes effect on the board together with the IPSECBIND and IPSECBINDITF bearer objects. That is, the IKEPROPOSAL MO does not take effect on any board when being configured, and takes effect on the board when the bearer MO (IPSECBIND or IPSECBINDITF) is configured.

  • If the authentication method of an IKE proposal is digital certificate authentication, the local certificate is of the ED25519 type, the peer certificate is not of the ED25519 type, and the signature hash algorithm negotiation switch is turned off on the peer, the IKE negotiation fails.

ENCALG Encryption Algorithm

Meaning: Indicates the encryption algorithm used in the IKE proposal. The Data Encryption Standard (DES) is an internationally used data encryption algorithm, which uses a 56-bit key. The 3DES is also an internationally used encryption algorithm, which uses a 168-bit key. The Advanced Encryption Standard (AES) is an advanced encryption algorithm, which provides three types of key of different lengths: 128, 192, and 256 bits. Therefore, different protection levels are available. For details, see RFC2401.AES_GCM_128 and AES_GCM_256 are AEAD encryption algorithms that provide both authentication and confidentiality protection. The values AES_GCM_128 and AES_GCM_256 are supported only by the UMPTe, UMPTg, UMPTga, UBBPe(excluding UBBP15), UBBPem, UBBPep, UBBPei, UBBPex2, UBBPf0, UBBPf1, UBBPg1, UBBPg2, UBBPg3, UBBPg4, UBBPg5, UBBPg6, UBBPg7 and UBBPg9 boards.

Disuse statement: In later versions, the values DES(DES) and 3DES(3DES) will be removed from the value range of this parameter. In the current version, these values can still be configured and take effect. Therefore, you are not advised to use the values DES (DES) and 3DES (3DES).

Unit: None

AUTHALG Authentication Algorithm

Meaning: Indicates the authentication algorithm used in the IKE proposal. IKE uses hashed message authentication code (HMAC) or cipher block chaining (CBC) for identity authentication and data integrity check. For details about HMAC, see RFC4306. HMAC currently supports four hash functions: message digest algorithm 5 (MD5), secure hash algorithm 1 (SHA1), secure hash algorithm 256 (SHA256), and secure hash algorithm 384 (SHA384). For details about the hash functions, see RFC2409. The value SHA384 is supported only by the UMPTg, UMPTga, UBBPg2, UBBPg3, UBBPg4, UBBPg5, UBBPg6, UBBPg7, and UBBPg9 boards. MD5, SHA1, SHA256 and SHA384 verify data by means of integrity protection. SHA384, SHA256, SHA1, and MD5 provide security levels in a descending order. CBC currently supports AES_XCBC_96, which is an enhancement to CBC. For details about AES_XCBC_96, see RFC3566. In addition, AES_GCM_128 and AES_GCM_256 are AEAD encryption algorithms in the IKE proposal. They can provide both identity authentication and data integrity check. SHA256, SHA384 and AES_XCBC_96 apply only to IKEv2.

Disuse statement: In later versions, the value MD5(MD5) will be removed from the value range of this parameter. In the current version, this value can still be configured and take effect. Therefore, you are not advised to use the value MD5(MD5).

GUI Value Range: MD5(MD5), SHA1(SHA1), AES_XCBC_96(AES_XCBC_96), SHA256(SHA256), SHA384(SHA384)

Unit: None

Actual Value Range: MD5, SHA1, AES_XCBC_96, SHA256, SHA384

MML Default Value: SHA256(SHA256)

Recommended Value: SHA256(SHA256)

Parameter Relationship:

DHGRP Diffie-Hellman Group

Meaning: Indicates the Diffie-Hellman (DH) group of the IKE proposal. The core technology used in an IKE proposal is the Diffie-Hellman (DH) exchange technology. The DH exchange technology is used to calculate private information based on public information. It is mathematically proven that decrypting the DH information is impractical due to calculation complexity. The Diffie-Hellman group specified by the value DH_GROUP14 or a value indicating a later algorithm provides better security but consumes more CPU resources. Therefore, set this parameter based on both the security concern and the CPU load. The values DH_GROUP19 and DH_GROUP20 are supported only by the UMPTa, UMPTb, UMPTe, UMPTg, UMPTga, UBBPg2, UBBPg3, UBBPg4, UBBPg5, UBBPg6, UBBPg7, UBBPg9 and UMDU boards.

Disuse statement: In later versions, the values DH_GROUP1(768-bit Diffie-Hellman Group) and DH_GROUP2(1024-bit Diffie-Hellman Group) will be removed from the value range of this parameter. In the current version, these values can still be configured and take effect. Therefore, you are not advised to use the values DH_GROUP1(768-bit Diffie-Hellman Group) and DH_GROUP2(1024-bit Diffie-Hellman Group).

GUI Value Range: DH_GROUP1(768-bit Diffie-Hellman Group), DH_GROUP2(1024-bit Diffie-Hellman Group), DH_GROUP14(2048-bit Diffie-Hellman Group), DH_GROUP15(3072-bit Diffie-Hellman Group), DH_GROUP19(256-bit ECC Diffie-Hellman Group), DH_GROUP20(384-bit ECC Diffie-Hellman Group)

Unit: None

Actual Value Range: DH_GROUP1, DH_GROUP2, DH_GROUP14, DH_GROUP15, DH_GROUP19, DH_GROUP20

MML Default Value: DH_GROUP19(256-bit ECC Diffie-Hellman Group)

Recommended Value: DH_GROUP19(256-bit ECC Diffie-Hellman Group)

Parameter Relationship: None

Service Interrupted After Modification: No (And no impact on the UE in idle mode)

Impact on Radio Network Performance: When this parameter is set to DH_GROUP14, DH_GROUP15, DH_GROUP19, or DH_GROUP20, the CPU usage temporarily increases during IKE negotiation.

Applicable Mode: G, U, L, N

DURATION ISAKMP SA Duration

Meaning: Indicates the life cycle of an ISAKMP SA. ISAKMP refers to Internet Security Association and Key Management Protocol, and SA refers to security association.

IKE negotiation requires a long time to calculate Diffie-Hellman (DH) keys. It is recommended that this parameter be set to greater than 10 minutes so that the update of the ISAKMP SA does not affect the secure communication.

Before the SA life cycle elapses, local and peer ends will negotiate with each other to generate a new SA to replace the original one. The new SA is used upon completion of the negotiation, and the original SA is automatically removed once its life cycle elapses.

GUI Value Range: 60~604800

Unit: s

Actual Value Range: 60~604800

MML Default Value: 86400

Recommended Value: 86400

REAUTHSW IKE Reauthentication Switch

Meaning: Indicates whether to enable the IKEv2 re-authentication. Reauthentication is done by creating a new IKE SA from scratch, creating new Child SAs within the new IKE SA, and finally deleting the old IKE SA (which deletes the old Child SAs as well). For details, see RFC5996. When this parameter is set to OFF, the BS starts the IKEv2 re-authentication only when the BS serves as the initiation end and receives the re-authentication lifetime notification from the peer end. When this parameter is set to ON, if the BS serves as the initiation end and receives the re-authentication lifetime notification from the peer end, the BS starts the IKEv2 re-authentication using the smaller one between the re-authentication lifetimes at the local and peer ends. When this parameter is set to ON, if the BS does not receive the re-authentication lifetime from the peer end, the BS starts the IKEv2 re-authentication using the re-authentication lifetime at the local end. If the value of this parameter is modified from OFF to ON via the command MOD IKEPROPOSAL, the system will start one re-authentication immediately. The DSP IKESA command can be executed to query the IKE re-authentication lifetime used by the BS.

This parameter is invalid for IKEv1.

GUI Value Range: OFF(Off), ON(On)

Unit: None

Actual Value Range: OFF, ON

MML Default Value: ON(On)

Recommended Value: None

Parameter Relationship: None

Service Interrupted After Modification: No (And no impact on the UE in idle mode)

Impact on Radio Network Performance: None

Applicable Mode: G, U, L, N

Example

To add an IKE proposal with the parameters as follows: Proposal ID: 10, IKE Reauthentication Switch: ON, run the following command: 
ADD IKEPROPOSAL: PROPID=10, REAUTHSW=ON;
