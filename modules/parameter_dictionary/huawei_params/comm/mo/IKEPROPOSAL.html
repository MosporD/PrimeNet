IKEPROPOSAL

TRANSPORT
  +-IKEPROPOSAL

Description

This MO defines a combination of security-related parameters such as encryption algorithms and authentication algorithms used by the Internet Key Exchange (IKE). The corresponding IKE security proposal is referenced by the IKE peer based on the number of the security proposal.

Effective Scenario

Immediately

Related Parameters

Table 2 and Table 3 describes the parameters related to this MO.

Table 2 Configuration parameters

Parameter

Description
Proposal ID

Indicates the ID of the IKE proposal.
Encryption Algorithm

Indicates the encryption algorithm used in the IKE proposal. The Data Encryption Standard (DES) is an internationally used data encryption algorithm, which uses a 56-bit key. The 3DES is also an internationally used encryption algorithm, which uses a 168-bit key. The Advanced Encryption Standard (AES) is an advanced encryption algorithm, which provides three types of key of different lengths: 128, 192, and 256 bits. Therefore, different protection levels are available. For details, see RFC2401.AES_GCM_128 and AES_GCM_256 are AEAD encryption algorithms that provide both authentication and confidentiality protection. The values AES_GCM_128 and AES_GCM_256 are supported only by the UMPTe, UMPTg, UMPTga, UBBPe(excluding UBBP15), UBBPem, UBBPep, UBBPei, UBBPex2, UBBPf0, UBBPf1, UBBPg1, UBBPg2, UBBPg3, UBBPg4, UBBPg5, UBBPg6, UBBPg7 and UBBPg9 boards.
Authentication Algorithm

Indicates the authentication algorithm used in the IKE proposal. IKE uses hashed message authentication code (HMAC) or cipher block chaining (CBC) for identity authentication and data integrity check. For details about HMAC, see RFC4306. HMAC currently supports four hash functions: message digest algorithm 5 (MD5), secure hash algorithm 1 (SHA1), secure hash algorithm 256 (SHA256), and secure hash algorithm 384 (SHA384). For details about the hash functions, see RFC2409. The value SHA384 is supported only by the UMPTg, UMPTga, UBBPg2, UBBPg3, UBBPg4, UBBPg5, UBBPg6, UBBPg7, and UBBPg9 boards. MD5, SHA1, SHA256 and SHA384 verify data by means of integrity protection. SHA384, SHA256, SHA1, and MD5 provide security levels in a descending order. CBC currently supports AES_XCBC_96, which is an enhancement to CBC. For details about AES_XCBC_96, see RFC3566. In addition, AES_GCM_128 and AES_GCM_256 are AEAD encryption algorithms in the IKE proposal. They can provide both identity authentication and data integrity check. SHA256, SHA384 and AES_XCBC_96 apply only to IKEv2.
Authentication Method

Indicates the authentication mode used in the IKE proposal. For details, see RFC2409 and RFC7427.
Diffie-Hellman Group

Indicates the Diffie-Hellman (DH) group of the IKE proposal. The core technology used in an IKE proposal is the Diffie-Hellman (DH) exchange technology. The DH exchange technology is used to calculate private information based on public information. It is mathematically proven that decrypting the DH information is impractical due to calculation complexity. The Diffie-Hellman group specified by the value DH_GROUP14 or a value indicating a later algorithm provides better security but consumes more CPU resources. Therefore, set this parameter based on both the security concern and the CPU load. The values DH_GROUP19 and DH_GROUP20 are supported only by the UMPTa, UMPTb, UMPTe, UMPTg, UMPTga, UBBPg2, UBBPg3, UBBPg4, UBBPg5, UBBPg6, UBBPg7, UBBPg9 and UMDU boards.
ISAKMP SA Duration

Indicates the life cycle of an ISAKMP SA. ISAKMP refers to Internet Security Association and Key Management Protocol, and SA refers to security association.

IKE negotiation requires a long time to calculate Diffie-Hellman (DH) keys. It is recommended that this parameter be set to greater than 10 minutes so that the update of the ISAKMP SA does not affect the secure communication.

Before the SA life cycle elapses, local and peer ends will negotiate with each other to generate a new SA to replace the original one. The new SA is used upon completion of the negotiation, and the original SA is automatically removed once its life cycle elapses.
PRF Algorithm

Indicates the Pseudo-random Function (PRF) algorithm used in IKEv2. The PRF algorithm is used to generate the materials required for IKE authentication and encryption. For details about how to generate materials, see RFC4306. The value HMAC_SHA384 is supported only by the UMPTg, UMPTga, UBBPg2, UBBPg3, UBBPg4, UBBPg5, UBBPg6, UBBPg7 and UBBPg9 boards.
IKE Reauthentication Switch

Indicates whether to enable the IKEv2 re-authentication. Reauthentication is done by creating a new IKE SA from scratch, creating new Child SAs within the new IKE SA, and finally deleting the old IKE SA (which deletes the old Child SAs as well). For details, see RFC5996. When this parameter is set to OFF, the BS starts the IKEv2 re-authentication only when the BS serves as the initiation end and receives the re-authentication lifetime notification from the peer end. When this parameter is set to ON, if the BS serves as the initiation end and receives the re-authentication lifetime notification from the peer end, the BS starts the IKEv2 re-authentication using the smaller one between the re-authentication lifetimes at the local and peer ends. When this parameter is set to ON, if the BS does not receive the re-authentication lifetime from the peer end, the BS starts the IKEv2 re-authentication using the re-authentication lifetime at the local end. If the value of this parameter is modified from OFF to ON via the command MOD IKEPROPOSAL, the system will start one re-authentication immediately. The DSP IKESA command can be executed to query the IKE re-authentication lifetime used by the BS.

This parameter is invalid for IKEv1.
IKE Reauthentication Lifetime

Indicates the life cycle of IKEv2 re-authentication. It is recommended that this parameter be set to a value greater than that of the ISAKMP SA Duration parameter. Otherwise, the ISAKMP SA Duration parameter becomes invalid.

This parameter is invalid for IKEv1.
Signature Hash Algorithm Negotiation Switch

Indicates whether to enable the digital signature authentication method (see RFC7427) and support signature hash algorithm negotiation.

If this parameter is set to ENABLE, the digital signature authentication method is used, signature hash algorithm negotiation is supported, and the base station sends a SIGNATURE_HASH_ALGORITHMS notification packet when initiating negotiation. If this parameter is set to DISABLE, the digital signature authentication method is not used, signature hash algorithm negotiation is not supported, and the eNodeB does not send SIGNATURE_HASH_ALGORITHMS notification packets when initiating negotiation.
RSA Padding

Indicates the RSA padding mode when the digital signature authentication method (see RFC7427) is used.

If this parameter is set to PKCS1V15, the RSASSA_PKCS1V15 padding mode is used for RSA signatures. If this parameter is set to PSS, the RSASSA_PSS padding mode is used for RSA signatures.
